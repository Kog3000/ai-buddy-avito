# Спецификация: агент AI-buddy

## Назначение
Агент отвечает стажёру в чате, выполняет оргдействия через MCP-инструменты корпоративных сервисов
и показывает следующие шаги адаптации. Агент **сокращает рутинные обращения к наставнику**, но не заменяет
содержательную работу наставника.

## Архитектура принятия решений
1. **NLU** (`app/agent/nlu.py`) — детерминированное определение намерения и слотов (даты, ресурсы, уровни прав).
   Учитывает состояние диалога (`ConversationState`): ожидание даты, ресурса, формулировки цели.
2. **Оркестратор** (`app/agent/agent.py`) — обработчик на каждое намерение; все обращения к данным — через `MCPClient`.
3. **RAG** — поиск BM25 по стемам (`app/services/kb.py`) только среди доступных пользователю материалов;
   при наличии LLM — синтез ответа по найденным материалам (`app/agent/prompts.py`).
4. **Карточки** — изменяющие действия оформляются как карточка подтверждения; действие выполняется только
   по нажатию кнопки (отдельный вызов `handle_action`).

---

### Requirement: Подтверждение изменяющих действий
Агент НЕ ДОЛЖЕН вызывать инструменты с `requiresConfirmation=true` из обработки текстового сообщения.

#### Scenario: Запрос доступа
- **WHEN** стажёр пишет «Нужен доступ к Stash»
- **THEN** агент возвращает карточку `confirm` с полями «Уровень прав», «Проект», «Обоснование» и кнопкой `access_confirm`
- **AND** заявка в сервисе доступов не создаётся до нажатия кнопки
- Тест: `test_access_single_flow`

#### Scenario: Результат действия сохраняется и показывается
- **WHEN** пользователь подтверждает карточку
- **THEN** агент вызывает MCP-инструмент, показывает карточку `request_status` со статусом из сервиса
- **AND** заявка видна в разделе «Мои заявки» и в истории чата
- Тест: `test_access_bundle_flow`, `test_requests_and_approvals_api`

### Requirement: Ответы на вопросы по базе знаний с учётом контекста
#### Scenario: Ответ с источниками
- **WHEN** стажёр задаёт вопрос, для которого есть материал со score ≥ `KB_MIN_SCORE`
- **THEN** ответ содержит текст материала (или синтез LLM) и список источников со ссылками
- **AND** материалы своей команды ранжируются выше (×1.15), ответы наставников из FAQ — ×1.1
- Тест: `test_kb_answer_with_sources_and_checklist_link`, `test_kb_search_relevance`

#### Scenario: Связь с чек-листом
- **WHEN** найденный материал привязан к невыполненной задаче чек-листа
- **THEN** агент предлагает отметить задачу выполненной (карточка с `task_done`)

#### Scenario: Контекстные вопросы
- **WHEN** стажёр спрашивает «Кто мой наставник?», «Мои встречи», «Что дальше?»
- **THEN** ответ строится из профиля, календаря и чек-листа текущего пользователя
- Тест: `test_context_answers`

### Requirement: Честный «не знаю» и эскалация
#### Scenario: Нет ответа
- **WHEN** релевантных материалов нет
- **THEN** агент говорит, что ответа нет, и предлагает передать вопрос наставнику (карточка `escalate_confirm`)
- **AND** агент не выдумывает регламенты
- Тест: `test_not_found_escalation_and_faq_reuse`

#### Scenario: Повторное использование ответа наставника
- **WHEN** наставник ответил и отметил «Добавить в FAQ»
- **THEN** ответ приходит стажёру в чат, а следующий такой же вопрос закрывается из базы знаний без наставника

### Requirement: Неблокирующий интерфейс и деградация
#### Scenario: Асинхронная обработка
- **WHEN** пользователь отправляет сообщение
- **THEN** `POST /api/chat/send` отвечает `202` с `job_id` за < 1 с; ответ агента приходит через опрос `/api/chat/jobs/<id>`
- **AND** интерфейс показывает индикатор ожидания, через 6 с — расширенный статус, через 60 с — ошибку с кнопкой «Повторить»
- Тест: `test_async_jobs_use_thread_pool`, E2E `test_full_journey`

#### Scenario: Сбой LLM
- **WHEN** LLM недоступна, вернула ошибку, пустой или некорректный ответ
- **THEN** агент отвечает офлайн из базы знаний и пишет `meta.llm_fallback`
- Тест: `test_llm_failures_fall_back_to_offline`

#### Scenario: Сбой агента
- **WHEN** обработка упала с исключением
- **THEN** задача получает статус `error`, интерфейс показывает «Повторить»
- Тест: `test_chat_job_failure_is_reported`

### Requirement: Проактивность (ИИ-крон)
#### Scenario: Смена статуса заявки
- **WHEN** сервис доступов/отсутствий меняет статус заявки
- **THEN** агент пишет стажёру в чат с карточкой статуса; при выдаче всех основных доступов закрывает задачу чек-листа
- Тест: `test_access_policy_auto_approve_and_base_checklist`

#### Scenario: Ежедневное напоминание
- **WHEN** ИИ-крон вызывает `POST /api/cron/run` (флаг `proactive_nudges` включён)
- **THEN** каждый стажёр получает не более одного напоминания в день о следующем шаге; хвосты прошлых этапов помечаются
- Тест: `test_cron_nudges`, `test_cron_respects_flag`

## Промпт LLM
Системный промпт — `app/agent/prompts.py::SYSTEM_PROMPT`. Ключевые правила: отвечать только по переданным
материалам; не называть тестовые материалы регламентами Авито; не обещать выполнение действий; не раскрывать
материалы вне контекста; не обсуждать чувствительные ПДн.
